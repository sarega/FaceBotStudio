# Paid Registration implementation audit

Reviewed the uncommitted workspace on 2026-11-16 against [PRD v0.2](../prd-paid-registration-v0.2.md) and all five Phase 0 documents. The implementation is suitable for continued local integration. Production acceptance remains open.

## Fixes made during review

1. **Proof privacy and validation.** Full JPEG, PNG and WebP raster decode with Sharp rejects corrupt files, unsupported formats, oversized images and animation. Original accepted bytes are encrypted with AES-256-GCM using a fresh nonce and associated event, booking, attempt and MIME data. The authenticated staff response uses no-store, nosniff and a sandbox policy. An audit event records proof views. A missing key disables new public enrollment and uploads. The original SHA-256 remains available for duplicate detection. [Sharp constructor and decoder options](https://github.com/lovell/sharp/blob/main/docs/src/content/docs/api-constructor.md).
2. **Migration and transaction concurrency.** A database-scoped PostgreSQL advisory lock serializes migration runners before checking the migration ledger. Each migration and ledger entry still commit together. Paid creation also checks the event and registration window inside the event transaction. An unpublished, closed or cancelled event cannot accept a new paid hold. Existing successful command replays retain their original result.
3. **Financial idempotency.** Approval checks already verified Direct Ticketing references before recording a paid settlement. Paid-to-paid duplicates are guarded by database uniqueness across event locks, and the PostgreSQL adapter returns the same conflict for a concurrent unique-index violation. Idempotent approval still creates one notification and one credential per attendee.
4. **Admission consistency.** The browser camera callback previously discarded paid credentials before calling the paid check-in endpoint. It now forwards paid credentials and omits the bearer value from the last-scan display. Both QR rendering and live scan reject cancelled or archived events. The opaque random credential differs from the proposed signed token and requires an authorized, live database lookup.
5. **Messenger.** Thai and English requests with an explicit headcount, category code and complete attendee names now enter the same durable quote flow as the structured commands. Ambiguous requests ask for clarification. An explicit confirmation with the quote ID is required to hold capacity. Matching runs only for paid events, so ordinary legacy-event conversations still reach the original bot. Proof and QR requests return authenticated links. The inbound attachment itself is not accepted as payment evidence.

## Release gaps and risk

- **Existing evidence.** Older proof rows written by the uncommitted pre-hardening implementation contain plaintext. They are not rewritten automatically and the new read path fails closed on them. Before upgrading a database that holds such rows, inventory them securely and plan an offline re-encryption and verification pass. Treat pre-upgrade backups as containing plaintext. Keep the same independently generated 32-byte hex key across replicas and in controlled recovery storage. Loss or replacement of the key without re-encryption makes existing ciphertext unreadable.
- **Shared receivers.** The paid reviewer detects legacy references already recorded at review time. Legacy Direct Ticketing writers still do not acquire a common settlement claim. Concurrent claims across the two products can therefore record the same transfer. Use separate receiver accounts for the pilot or agree and implement a cross-domain claim and reconciliation policy before using shared receivers.
- **Operations and financial reporting.** A timely valid proof pauses sweeping indefinitely until staff review. There is no configured escalation, late-proof resolution, reinstatement, cancellation, extension, refund record or staff revocation workflow. Existing duplicate or out-of-window approvals return a conflict for staff follow-up. The summary shows verified totals and unsettled booking totals, with incomplete support for observed receipts, refunds and remaining balances.
- **Messenger language and delivery.** The natural-language parser covers an explicit Thai/English booking grammar, not open-ended conversation, mixed-category prose or clarification across turns. Structured commands support mixed-category bookings. Configured required seminar forms use the web flow. Signed webhook fixtures use inline handling and inspect outbox jobs. Production Redis, Facebook Graph, email delivery and other provider retry behavior remain unverified.
- **Performance and live acceptance.** Capacity safety was tested with separate database connections and SQLite processes. Peak throughput, parallel image decoding under load, camera-device behavior, and production backup restore have not been measured. Rollback should disable new enrollment while retaining a version capable of managing already-created paid bookings.

## Follow-up hardening — 16 November 2026

- **Cross-domain transaction-reference collision:** PostgreSQL paid approvals, direct-order approvals, and direct-ticket approvals now take a shared transaction-scoped advisory lock on the normalized bank transaction reference. The direct approval paths then check existing verified paid settlements before issuing tickets, eliminating the paid/direct review time-of-check/time-of-use race when a reference is supplied. SQLite uses its serialized write transactions with the same direct-side duplicate check. The reverse paid-side legacy lookup remains in place. Both collision directions have a SQLite regression fixture. The direct admin/API and webhook routes return HTTP 409 for the explicit duplicate error.
- **Pending payment verification escalation:** The pre-existing autonomous Telegram Admin Agent now flags paid bookings whose submitted attempts are awaiting review for at least 24 hours, restricted to the agent's organization's active-event list and its configured event scope. This is an operator alert, not an automatic hold release or payment approval. Its threshold is currently hardcoded at 24 hours and should become configurable before launch.
- **Remaining guardrail:** Legacy direct approvals that lack any bank transaction reference cannot be reliably deduplicated. No new financial reconciliation or refund actions were added. PostgreSQL cross-domain lock behavior still needs a dedicated concurrent integration test against a disposable PostgreSQL server.


## Release 0.8.0 operational completion — 2026-11-16

- Added role-restricted Admin Booking Operations UI and event-scoped API to locate a paid booking by reference and perform audited, versioned, idempotent hold extension, expiration reinstatement, unpaid cancellation, and **record of an already-completed full refund**. Reinstatement is subject to current event registration availability plus live event/category capacity checks; refund recording requires an external settlement reference and disallows refunds after check-in. A completed refund revokes outstanding credentials.
- Added migration 049 for an immutable full-refund record, consistently applied by both adapters. Refund action is **not** a bank transfer and does not implement partial refunds, chargebacks, or reconciliation.
- Added basic Admin operations to the existing Paid Registration Reviews section, cross-system reference conflict checks, and review-age alerts through the configured autonomous Telegram agent.
- The public paid flow remains opt-in with PAID_REGISTRATION_PUBLIC_ENABLED=1, an independently generated 32-byte encryption key in PAID_PROOF_ENCRYPTION_KEY, configured organizer receiving profile, and an eligible event. Never enable production payment intake before checking environment secrets, database migrations and webhook/worker routing.
- Outstanding production acceptance: real payment reconciliation, configurable review escalation/remainder policy, provider delivery and recovery, PostgreSQL cross-domain concurrency test, and operational backup/restore. Pilot with synthetic/controlled transactions first.

- Optional 24-hour payment reminder queueing uses the existing notification outbox with a per-booking idempotency key, a worker-side opt-in flag PAID_REGISTRATION_REMINDERS_ENABLED, and delivery-time checks for active unpaid bookings and transactional email preference. This flag remains off by default; no reminders were sent to real customers during local verification.

## 0.8.3 — Internal external/manual payments

- Added additive migration 050: paid_event_settings.payment_mode defaults to promptpay to preserve older events; accepts external_manual explicitly.
- External/manual bookings do not require receiver snapshot or payment-proof encryption. The booking stores no fictitious receiving account.
- Staff confirm independently verified full payment via existing role-restricted review API, a unique external reference and EXTERNAL_MANUAL namespace; existing capacity deadlines, idempotency, duplicate-reference checks, audit log and QR-after-confirmation remain in effect.
- Paid website still uses verified customer-account authentication and server deployment controls. CUSTOMER_APP_ENABLED=1 and PAID_REGISTRATION_PUBLIC_ENABLED=1 are required for web booking; customer account registration must be enabled if new accounts are expected.
- Existing events can change payment mode in Paid Registration Settings; this does not require deleting or recreating the event.
- No funds are transferred by this system. Anonymous/no-account guest registration is a separate authenticated-recovery design decision.

- External/manual bookings waiting for operator verification are included in the Admin Review Queue even without a slip or booking-reference filter; per-booking receiver snapshots govern verification so later event payment-mode changes do not retroactively alter existing bookings.
