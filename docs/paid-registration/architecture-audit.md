# Phase 0 — Architecture audit

Reviewed FaceBotStudio main at `1ded017` on 2026-11-16 against [PRD v0.2](../prd-paid-registration-v0.2.md). Findings below refer to the checked-out implementation. The focused existing suite passed 33/33, including temporary SQLite adapter tests. An isolated local web process using a fresh SQLite file returned HTTP 200 from `/api/health` with `status: ok`, `database: sqlite` and `runtime: web`. The smoke test covered startup and database health. PostgreSQL paths were inspected in source. Production configuration, data, webhook delivery and deployed revision were not verified. The local configuration points at localhost and no PostgreSQL connection was configured for this audit.

| Area | Observed path and transaction boundary | Paid Registration design |
|---|---|---|
| Public/free | `server.ts:4879–5145` builds the public payload from event settings, capacity and legacy ticketing flags. `POST /api/public/events/:slug/register` (~16780) resolves the public slug and availability, validates personal details, uses a new random web sender ID, then calls `createRegistration` (~11676). That wrapper starts Telegram/email work after the DB write. The response can contain a ticket immediately. Staff `POST /api/registrations` (~17382) and multiple bot paths (~8811, 9028, 12407) converge on the same wrapper. | Dedicated paid booking path. Gate every legacy registration creation path for explicitly paid events, including admin batch and bot fallback. Preserve legacy routes and response formats for legacy events. |
| Capacity | `getEventCapacitySnapshot` (~480) uses registration counts and `reg_limit`. PostgreSQL `createRegistration` (959) locks the event row, then checks active count/duplicate and inserts on one client. Settings are read before the lock. SQLite `createRegistration` (1737) reads active rows and inserts without an explicit transaction spanning both operations. Name-match and random sender IDs are unsuitable for booking idempotency. | Count paid attendee rows under one event lock/write transaction. Include checked-in attendees in confirmed capacity. Gate settings updates and mode changes with the same lock. Keep legacy SQLite behavior outside this change. |
| Direct checkout | `POST /api/public/events/:slug/orders` (~16553) requires a verified customer and resolves checkout settings, availability, organizer receiver and pricing. `/direct-orders` (~16622) is a separate public entry point. `createDirectOrder` (PG 1760, SQLite 2465) expires old holds in a separate call, then atomically inserts order, ticket children, initial payment attempt and updates allocated seats. PostgreSQL locks seats; SQLite uses a synchronous transaction. Migrations 020/021 enforce a unique active ticket per seat and a unique non-null verified ticket reference. | Keep direct checkout intact. A paid attendee consumes a capacity unit with no performance, allocated seat or issued direct ticket. |
| Direct payment | `/api/customer/orders/:id/payment-proof` (~15100) requires verified owner and bounded raw upload. Adapter submit locks order in PG and uses a SQLite transaction; it writes base64 to order, tickets and latest attempt and sets a 24-hour hold. Direct expiry includes `payment_submitted`. Staff order decision (~18331) changes order, ticket, seat and latest attempt in one transaction, then runs route-level audit/delivery. Adapter accepts a decision without a supplied independently verified amount. `/api/webhook/direct-payments` (~16724) HMAC-verifies a request and updates a **single direct ticket** using reference, amount, receiver and time checks at the route. | Separate payment evidence and approval. No paid approval webhook in MVP. Compare trusted exact amounts inside the paid transaction. Never inherit the rolling 24-hour extension or direct expiry rules. |
| Payment schema | Migration 031 requires `direct_orders.performance_id` and `payment_attempts.order_id` pointing to a direct order. Attempts are unique by order and sequence, and verified non-null references are unique inside that table. Migration 021 has a separate direct-ticket reference index. Adapter types `DirectOrderRow` and `PaymentAttemptRow` mirror the direct contract. SQLite embeds comparable DDL and upgrade helpers in its adapter. | Use separate paid attempts. Existing indexes do not enforce uniqueness across payment domains. Expose cross-domain concerns explicitly before rollout. |
| Organizer finance | Migrations 034/035 have separate organization- and organizer-profile-level records, versioning, readiness and PromptPay-only method constraints. `resolveEventOrganizerFinancialProfile` (~4794) resolves a profile within the event owner organization or the legacy organization fallback. `GET/POST /api/organizers/:id/financial-profile` (~18785) enforce owner/admin and organization scope. Browser responses mask identifiers. | Reuse scoped lookup, readiness and PromptPay generation. Snapshot selected receiver/profile version; keep snapshots private. Bank transfer needs an explicit scoped configuration extension. Do not infer tax, fees, payout or receipt issuance from direct pricing flags. |
| Dashboard | `GET /api/registrations` (~17228), adapter per-event counts/activity, `src/App.tsx` (~7664), EventWorkspace and Reports read legacy registrations and direct ticket data. Existing registration status/delete actions operate on legacy records. | Reuse event workspace, role and filter/export infrastructure. Add separate paid queries and DTOs, including verified amounts once per booking and attendee counts separately. |
| QR and check-in | `/api/registration-tickets/:id.<format>` (~18575) uses ticket access tokens bound to ticket and format. `performCheckinForRegistration` (~5238) checks ID, event and cancellation, then invokes adapter update. Scanner `src/App.tsx:8003` and staff/check-in-access endpoints (~15704, 15763, 17427) support legacy and direct routes. Direct tickets have their own issue/check-in state. | Reuse render/scanner surfaces and scoped check-in sessions. Add paid credential routing and verify live booking/payment/credential under a lock before writing attendance. Existing download tokens and registration IDs are unsuitable as paid admission credentials. |
| Media | `/api/private-media/:scope/:fileName` (~14662) has scope/file token and staff authorization mechanics. Direct proof uses a scoped staff ticket route (~18395), with base64 held in DB records. | Reuse validation/token patterns where applicable. Dedicated private storage and booking-level authorization, including per-object access, are required for slips. |
| Notifications | `backend/runtime/notificationWorker.ts` periodically dispatches `backend/notifications/outbox.ts`. Migration 028 has unique delivery keys and 037 adds Facebook. Adapter claiming uses PG `FOR UPDATE SKIP LOCKED` or a SQLite transaction, with worker ownership and retry transitions. Legacy registration wrapper schedules work after commit, so a process crash can leave a gap. | Persist paid jobs in the confirmation transaction by adding a transaction-bound insert into the existing outbox. Sender rechecks entitlement and supports provider dedup where available. |
| Messenger | `POST /api/webhook` (~21328) verifies signature, normalizes page events, enqueues in production and returns retry if queue unavailable. `processFacebookInboundJob` (~13968) and the event chat tool pipeline resolve sender/page and event routing. `getSystemInstruction` (~554) selects latest meaningful customer language with Thai fallback. | Reuse ingress, routing and language. Derive tool authorization from the trusted session and require a durable account binding. Add persistent action dedup beyond queue retention. Keep payment review tools out of the customer toolset. |

`backend/db/index.ts` chooses PostgreSQL via `DATABASE_URL`, otherwise SQLite. `backend/db/migrate.ts` applies ordered PostgreSQL SQL files with each file and ledger insert in one transaction. The preflight ledger query is outside that transaction, so serialize migration runners. SQLite initializes/upgrades in code with foreign keys enabled.

Highest-risk tests for the next phase are cross-connection oversubscription, mode bypass via legacy endpoints, proof-versus-expiry and cancellation-versus-scan races, monetary reference reuse, and notification gaps after transaction commit. Existing direct, identity, scope, token and outbox tests provide regression baselines. See the [implementation tasks](implementation-tasks.md) for coverage gaps.
