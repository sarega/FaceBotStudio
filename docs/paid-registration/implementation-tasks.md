# Phase 0 — Implementation plan and gates

Start Phase 1 only after review approval. Each later phase follows the PRD sequence and depends on the preceding gate. Use disposable DBs, synthetic PII and stubbed delivery for routine tests.

| Phase | Ordered work | Review gate |
|---|---|---|
| 1 — Core | Resolve configuration and identity decisions. Add additive migrations, types and adapter commands. Add paid catalog/setup/create/detail and recovery. Gate legacy writes for explicit paid mode. Implement expiry command and minimal periodic sweep with bounded recovery; use the same operation for Phase 5 scheduling. Add web category/group/contact flow and show amount/deadline. Keep live enrollment disabled through payment readiness. | Verify SQLite legacy upgrade and clean setup plus PostgreSQL fresh/upgrade on a disposable server. Legacy inline, external, customer and staff ticketing route matrix. Group N holds N, rejects over quota without partial rows, replays after timeout, and expires once. Race with independent connections/processes, same and different command keys and concurrent settings edits. |
| 2 — Payment and admission | Freeze organizer receiver source, implement exact money validation, private proof storage and cleanup, manual review queue and trusted settlement records. Add transaction-bound audit/outbox/credentials, render and live scanner path. | Valid-before-cutoff proof wins against expiry when accepted first. Test exact cutoff, repeat/rejected/late proof, under/overpayment, duplicate references, concurrent review, cross-event/owner authorization, invalid MIME/size and orphan cleanup. Roll back injected failure between financial and credential/outbox writes. No pre-confirmation or revoked QR works. Per-attendee tokens scan once under concurrency and cancellation races. |
| 3 — Messenger | Wire account binding, versioned group draft, explicit confirmation, tool dedup, authorized status and proof link/intake, localized delivery and recovery. | Signed webhook fixtures through queue and handler, duplicate/replayed messages, lost session, timeout after successful DB write, page/event reassignment and Thai/English switching. Customer bot has no approval path or access to unrelated data. |
| 4 — Seminar and admin | Add versioned stay/transport/food definitions and validated answers. Build booking/group detail, search/filter/export, summaries and approved correction, extension, cancellation and reinstatement controls. | Tenant/event isolated searches, exports and proofs. Active and checked-in heads count once; receipts aggregate by booking, expired groups contribute no occupancy, refunds and exceptions reconcile. Concurrent reinstatement or group edit never overbooks. |
| 5 — Production readiness | Configure approved reminders, expiry/recovery scheduling, pending-proof escalation, Telegram admin alerts and daily outstanding summary. Observe queue lag, hold age, failed delivery, duplicate flags and private-media cleanup. Validate backup/restore, staging and pilot/rollback runbook. | Both adapters pass migrations and API suite. Stage end-to-end with real worker topology and authorized test payment, channels and scanner. Verify feature disable and continued service for existing paid obligations. Review deployment and rollback before explicit release. |

## Baseline and test map

- Existing focused run used `node --import tsx --test backend/db/{orderDomain,directTicketing,phase0Regression,notificationOutbox,customerIdentity,registrationSmsConsent,eventAssignments}.test.ts backend/{customerAuth,ticketAccess,privateMediaAccess,commerce}.test.ts` and passed 33/33. Adapter tests exercise temporary SQLite files. This is baseline evidence for current behavior.
- Add paired SQLite/PostgreSQL contract tests for new commands, route tests for permissions and DTOs, independent connection contention tests, and worker restart tests. Test crash after provider acceptance but before marking sent. Record provider-specific dedup behavior and define handling of ambiguous delivery. The outbox unique key prevents duplicate jobs, while provider delivery can remain at-least-once.
- Before enabling any pilot, inventory effective modes, event/organization mappings, finance readiness, enabled customer auth, existing active registrations, available private storage, reference overlap across rails, and worker topology. Restrict first activation to an event without legacy enrollment unless a reviewed accounting/occupancy cutover exists.
